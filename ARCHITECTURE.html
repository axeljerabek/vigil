2. Camera process recorder_pipeline.py — CameraAgent.run()

A dedicated process per camera (multiprocessing, spawn method). Connection setup, then an infinite loop processing every packet from the RTMP stream.

always, unthrottled (recording integrity) throttled (detection/preview only)
Core finding from today's debugging session: the throttle (frame_interval, reduces YOLO load) used to run before queueing — a skipped video packet tore a gap into the H.264 reference chain (P-/B-frames reference prior frames) and produced artifacts. Now: queueing always happens first, the throttle only affects detection/preview/filmstrip.

3. Recording (packet copy) no more re-encoding

Instead of re-encoding every frame, the already-compressed packets are copied straight into the output file — ~1000× faster per frame, quality = exactly what the camera produces.

Measured: 0.7 ms (remux) vs. 785.9 ms (real re-encoding) for 150 frames. No more .venv NVENC setup needed for recording itself — the GPU is now only needed for YOLO and the AI models.

4. Filmstrip & live preview reservoir sampling + background threads

Two independent background write paths, both decoupled from the time-critical recording loop — only a cheap array copy happens live, the actual writing runs asynchronously.

Both queues are deliberately daemon threads — they die instantly with the process. Without .join() before shutdown, not-yet-written filmstrip images could be lost — exactly the bug found and fixed today.

5. Post-processing / AI models postprocess.py — GPU-serialized

As soon as a recording finishes, web_ui.py starts postprocess.py as its own process. A file lock serializes all GPU access so multiple cameras don't block each other.

All steps write into the same .ai.json — every step reads first, merges, then writes, instead of blindly overwriting (today's fix: ai_analyze.py initially didn't do this and wiped out transcripts as a result).

6. Data storage filesystem + two SQLite databases

No central database for videos themselves — each recording lives as a file with sibling sidecar files. Only faces and the search index have their own SQLite databases.

7. Web UI (Flask) web_ui.py

A Flask process serves the dashboard, all API routes, and orchestrates pipeline restarts. Runs independently of the recording master process.

8. Process orchestration master process, start/stop, Docker vs. bare metal

A master process reads the camera configuration and starts one CameraAgent child process per enabled camera. Two deployment types run with the same code.

bugs found and fixed today, marked in the flow
The Docker deployment uses network_mode: host, bind-mounting streams.json, alerts/, and config.py directly from the host — both environments share the same configuration files but run as completely separate processes with their own Python interpreter.
